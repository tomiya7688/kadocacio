# 試合の操作・観測・差分契約 v1

[移行 #123](https://github.com/tomiya7688/kadocacio/issues/123) の境界。既存 [#22](https://github.com/tomiya7688/kadocacio/issues/22) の `MatchResult` と [#36](https://github.com/tomiya7688/kadocacio/issues/36) の再現入力・スコアボード・イベント契約を利用する。Pythonは実際の `Match` を動かす。Godotの読込/再出力検査は試合演算ではない。#124の初期状態・時計・固定更新・乱数基盤の実行範囲は [`Godot試合核.md`](Godot試合核.md) と分ける。

## 責務と呼出し

| 境界 | Python参照 | Node無しのGodot |
|---|---|---|
| 操作検証 | `scripts/core/match_operation.py` | `scripts/core/match_operation.gd` |
| 入力の復元 | `scripts/tools/match_contract_input.py` | `scripts/match/match_input_record.gd` |
| 操作の適用 | `scripts/match/match_session.py` | `scripts/match/match_kernel.gd`（#124基盤、物理/AIは未移行） |
| 独立した観測 | `scripts/match/match_observation.py` | `match_snapshot.gd` に生成、`match_trace_record.gd` に読込 |
| 最初の差分 | `scripts/core/match_trace_comparison.py` | `scripts/core/match_trace_comparison.gd` |

Pythonの `MatchSession(home, away, seed=…, venue_mode=…, ai_rethink_multiplier=…, max_steps=…)` は入力チームを複製し、`apply(operation)` と `observe(after_sequence=0)` を境界として提供する。`observe` は不変の `MatchObservation` を返し、`to_payload()` は毎回独立したJSON値を返す。画面へ選手・ボール・チームの可変内部オブジェクトを渡さない。

Godotの `MatchInputRecord.read(payload)` / `MatchTraceRecord.read(payload)` は `is_valid()` / `error` と `to_payload()` を提供する。返却データは深いコピー。`MatchTraceComparison.compare(expected, actual)` は差分レポートを返す。不正な観測は一致とせず、Pythonは `ValueError`、Godotはエラーと `same_observations: false` を返す。

これは移行検証用の追加境界。既存PythonのUI・リーグ・チューナーの入口は差し替えず、演算/AI/得点判定も変更しない。観測のJSON化は明示要求時のみで、従来の毎ステップ処理へ追加しない。

## 入力と操作

入力形式は `kadocalcio.match-contract-input`、`version: 1`。`repro_input` に既存 `kadocalcio.match-repro-input` v1の正規化済みhome/away、能力、監督、会場、固定ステップ、AI頻度、ステップ上限を包む。**このラッパー内だけ** `settings.seed` を10進文字列にする。元の再現入力APIは整数seedのままで変更しない。既存 `commands: []` は保持し、操作は新しい `operations` に置く。

```json
[
  {"kind": "START"},
  {"kind": "SET_SPEED", "value": 2},
  {"kind": "STEP", "dt": 0.05},
  {"kind": "PAUSE"},
  {"kind": "RESUME"}
]
```

- `START`: 列の先頭に一度だけ。既存 `Match.start_new()` を呼ぶ。再開始には別セッションを作る。
- `STEP`: `0 < dt <= 0.05` 秒の物理・AI更新を一回。速度倍率を掛けない。実時間1秒→試合内10秒は既存演算核が扱う。
- `SET_SPEED`: 1/2/3/5/10/100の表示希望値。ホストは実時間に応じた回数の `STEP` を供給する。時計だけを飛ばさない。
- `PAUSE` / `RESUME`: ホストによる停止/再開。停止中とFULLTIME後の `STEP` は更新しない。`observe` はいつでも可能。

未知の操作/追加フィールド、boolを使った数値、非有限dt、二重START、予算を超えるSTEP列は拒否する。入力列の予算検証では停止中のSTEPも数える。セッションの実更新数は停止中/FULLTIME後を数えない。キーと上限の正本は `scripts/core/match_protocol.py` と既存固定ステップ/倍速定義で、Godot向け `data/match_contract.json` は明示導出物。

`PlayerCommand` の名前と日本語ラベルも導出物に含む。AI判断はこの操作列で上書きしない。キック/パス等は今までの能力値依存の自動判断とし、観測の `command` で照合する。手動ジャンプや仮の結果式は追加しない。

## 観測列

形式は `kadocalcio.match-contract-trace` v1。`source` は `implementation`、`execution`、`rng`、`seed_text` を宣言し、`entries` に操作ごとの観測を入れる。

一件は `operation_index`（0始まりの操作順）、`snapshot`、`events`、`result`。`snapshot.step` は実更新回数なので、停止や設定操作では進まず同じ値になる。時計は秒、座標は既存シミュレーションのワールド単位（画面ピクセルではない）。平面は既存x/y、高さはz。描画投影は含めない。

- `status`: 既存 `MatchStatusSnapshot` の名称・スコア・時計・PLAYING等の状態・バナー・倍率。
- `simulation_elapsed` / `paused`: 演算経過とホスト停止。セットプレー準備中は演算経過が進んでも `status.game_time` は止まる。他会場を止める意味ではない。
- `home` / `away`: 得点・シュート・支配時間・戦術・攻撃方向と、選手のID/背番号/名前/役割/位置/目標/スタミナ/コマンド/退場。
- `ball`: xyz位置、xyz速度、所有者ID（非保持時null）。
- `restart` / `throw_in`: 種別・チーム側・位置・担当者・準備経過など。無い場合null。
- `pending_kick`: モーション中の選手・コマンド・対象選手/座標。無い場合null。
- 反則・カード・再開回数も状態に含める。

観測IDは `HOME:0` / `AWAY:0` のような**現在の出場ロスターの行番号**。背番号重複でも曖昧にしないための参照キーであり、永続選手IDではない。交代後の行は名前・背番号・役割と併せて読む。

`events` は既存 `MatchLogEvent` の発生順sequence（1始まり）・試合時計・演算経過・text。`observe(after_sequence)` のカーソルより新しいもののみ返し、操作列の捕捉ツールは最後のsequenceを次のカーソルにする。観測列でsequenceが巻き戻る/重複する入力は拒否する。既存8件のHUD表示キューとは別の履歴APIを使う。

`result` は未終了ならnull。FULLTIME時には既存 `MatchResult.to_payload()` の得点、シュート、支配時間、得点者、最終時計を複製する。途中の非null結果とFULLTIMEの結果欠落は、両実装で拒否する。途中観測を完走と偽らない。JSON値のみを認め、時計/得点/所有者/位置/選手判断/イベント/結果の主要必須値の型も検査する。未知の追加観測キーも保持・比較するが、入れ子を含む全JSON数値は有限かつ絶対値9e15未満に制限する。入力のversion/max_stepsにも共通の整数制約を適用する。大整数seedのみ十進文字列で別に保持する。

#124のGodot基盤は得点/結果集計が未移行で、時計だけの基盤試験がFULLTIMEになっても生の観測ではresultをnullのまま返す。この部分試験の終了状態は、上記v1観測列の「完走結果」として読込・比較できない。部分実装を架空の0-0完走へ変換せず、完成した結果集計が接続されるまで完走互換の認定対象から除外する。

## 数値と乱数

JSONの `1` と `1.0` は数学的な整数なら同じとする。boolは数値でない。整数観測は絶対値9e15未満とし、巨大seedは最大4096桁の符号付きASCII10進文字列で保持する（余白、先頭0、`-0` は不可）。`9223372036854788153` のようにint64/JSON浮動小数点の範囲を超えても、入力の読取りで桁落ちさせない。#124の `PythonRandomStream` はこの文字列から整数seedのMT初期状態を組み立てる。

標準GodotのVector2は32bit成分で、GDScriptのfloatとは精度が異なる。そのため座標のビット一致を要求せず、JSON観測をスカラーで比較する。[Godot公式Vector2の精度](https://docs.godotengine.org/en/stable/classes/class_vector2.html)

比較式は `abs(expected-actual) <= absolute + 1e-9 * max(abs(expected), abs(actual))`。以下の絶対許容差を使う。整数項目は相対差も0で厳密比較。

| 項目 | 絶対許容差 |
|---|---|
| 位置・速度・目標・再開位置 | 1e-3ワールド単位 |
| スタミナ | 1e-6 |
| 時計・その他の浮動小数点値 | 1e-8 |
| step/操作順/sequence/背番号/攻撃方向/得点/シュート/倍率/反則・カード/MT語・index・消費数・ビット値 | 0 |
| ID・状態・コマンド・イベント本文・null・bool | 厳密一致 |

これは最初の観測診断の許容差で、長時間の物理分岐が同一になる保証ではない。範囲変更は両言語のテストと導出契約を同時更新する。キー不足とnull、配列長の相違も別の差分として検出する。

Python参照は `random.Random` のMT19937を使用。Godotの標準RNGは公式文書でも実装詳細とされる別の生成器なので、**同じseed文字列だけで同一乱数列を仮定しない**。[Godot公式RNGの説明](https://docs.godotengine.org/en/stable/classes/class_randomnumbergenerator.html)

#124の乱数交換点は [`Godot試合核.md`](Godot試合核.md)。整数seed互換のMT19937と用途/呼出順/消費数を検証する。監査を使うと任意追加の `snapshot.rng` に状態と差分監査列を付ける。既存traceへ必須キーを追加せず、境界v1自体は入力seedと使用RNGの来歴を運ぶ。別RNGの統計評価を行うなら別モードで明示する。境界読込の成功や短い乱数fixture一致を全試合結果一致としない。

## 差分と開発コマンド

レポート形式 `kadocalcio.match-contract-diff` v1は `same_observations`、`scope`、両 `sources`、`first_difference` と状態/イベント/結果それぞれの最初の差分を返す。差分にはJSONの `path`、reason、expected/actual、entry/operation_index、実更新 `step`、categoryを含める。時系列で早い観測を先に、同一観測内ではsnapshot→events→result、辞書キーは名前順で比較する。seed相違は観測前のinput差分、末尾の欠落はmissing_entryとして出す。

`scope: contract_roundtrip` はGodotがPython観測を読み出し直しただけ。両者が実演算を宣言した場合は `simulation_observations`。いずれもこのレポートの `kernel_parity` は `not_evaluated` であり、サンプル一致だけで全演算互換を認定しない。Godotのfixture出力には `execution: contract_roundtrip` / `rng: not_executed/reference_observations_only` を明示する。

PowerShell、リポジトリルートで実行:

```powershell
.venv\Scripts\python.exe -m scripts.tools.godot_match_contract --write
.venv\Scripts\python.exe -m scripts.tools.godot_match_contract
.venv\Scripts\python.exe -m scripts.tools.godot_match_fixture --steps 96
.\run_godot.bat test
```

鮮度検査は古い契約を勝手に直さず停止する。fixtureはGit管理中の公開2チームで短い実試合を実行し、`user_data/logs/godot/match_contract/fixture.json` へ入力/観測/不正ケース/差分期待値を生成する。teams原本のSHA-256は成功/失敗/タイムアウト時も照合する。未追跡のチーム、`teams/カルチョビット/`、ユーザーセーブを読込/公開しない。

`run_godot.bat test` は実Godotで読み取り/再出力/差分期待値を照合し、Pythonでもネイティブ出力を比較する。出力は毎回新しい一時ディレクトリに作り、古い成功ファイルを使わない。最終差分は `user_data/logs/godot/match_contract/diff.json`。CIはWindows/Linuxで同じ経路を実行する。

別の観測列を既存fixtureと比較する場合:

```powershell
.venv\Scripts\python.exe -m scripts.tools.godot_match_fixture --fixture user_data/logs/godot/match_contract/fixture.json --actual native_trace.json
```

終了コードは0=観測一致、1=差分、2=入力/実行エラー。同じチーム能力・操作列・乱数条件から生成したtraceを渡すこと。レポートが自動でチーム/操作列全体の同一性まで証明するわけではない。通常プレイ、3D試合表示、90試合性能、旧セーブ互換、Godot演算核の一致はこの単位の検証対象外。
