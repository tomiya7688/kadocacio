# 試合再現性（段階的な導入）

## seedの入口

`Match(home_choice, away_choice, venue_mode, *, seed=整数)` は、選手・チームの生成より前に試合専用の乱数器を初期化する。同じチームデータ、設定、seed、固定ステップ入力から新しい `Match` を作れば、初期状態と試合進行を再現できる。`seed=None` は従来どおり非決定的で、試合テスト等の既存呼び出しを維持する。

試合層の乱数は `match.rng` を使い、プロセス共通の `random.seed()` は変更しない。同じ試合オブジェクトで `start_new()` を繰り返すことは再現契約の対象外であり、再生時には新しい `Match` を生成する。

## リーグ・評価

リーグの観戦試合と裏試合は、`league_fixture_seed()` で同じseedを計算する。既存の裏試合の算出式（`fixture_id:home_name:away_name` のUTF-8 SHA-256先頭8バイト）を保つ。ただし、これまでは選手生成後にseedを設定していたため、選手の初期乱数値と試合結果は変わり得る。AI評価の指定seedについては、下記の専用節で説明します。

裏試合の実行経路による初期化の差を防ぐため、`scripts/league/league_simulation_workers.py` の単独処理と同期バッチ処理は、どちらも共通seedを `Match(..., seed=...)` へ渡します。構築後の `rng.seed()` へ置き換えないでください。同期バッチも試合ごとの乱数器を持ち、バッチ全体で一つの乱数列を使い回しません。

同期する値は観戦側の演算経過秒数です。各試合のセットプレー準備による試合時計の停止は、他の試合を止める理由にはなりません。共有目標が負値になると、バッチ処理は観戦側のペース待ちを解除し、同じ固定ステップのまま残りを計算します。更新上限で止まった結果は `fulltime: false` / `finish_reason: step_limit` とし、完走結果に置き換えません。

開発者はGitルートで `python -m unittest discover -s tests -p test_match_seed_contract.py -v` と `python -m unittest discover -s tests -p test_league_simulation_session.py -v` を実行してください。試験は構築引数のseed、単独処理と同期バッチ処理の短区間の実状態、更新上限と通知の配線を確認します。模擬試合と実Matchの試験を分けており、子プロセス間通信・90分完走・90試合同時の性能を証明するものではありません。通常の利用者に追加の操作はありません。

## AI評価ジョブ

AI評価では、`scripts/tools/ai_evaluator.py` の `_run_evaluation_job` がジョブの指定seedを整数としてMatch構築時に渡します。リーグ対戦IDからseedを作る方式とは区別してください。評価対象をアウェーへ置いた場合も、得失点・保持率・平均スタミナは評価対象側から集計します。保持量の合計がゼロなら、保持率は0.5になります。

実時間の上限はマシンの負荷によって消費できる固定更新数が変わるため、同seedだけで終了時点まで一致するとは限りません。ジョブは実際の終了理由・更新回数・完走フラグを返し、目標時刻や実時間上限での停止を90分完走に置き換えません。再現を比較する際は、目標到達や更新数も確認してください。実測秒数は一致判定から分けて扱ってください。

開発者はGitルートで `python -m unittest discover -s tests -p test_ai_evaluator_job.py -v` を実行してください。構築seed・条件の引渡し・両側の集計・保持量ゼロは模擬試合で確認し、短い実Matchの繰り返しも確認します。90分完走や実子プロセスの試験ではありません。通常の利用者に追加の操作はありません。

## 描画あり・なしの検証

`python -m scripts.tools.match_repro_check` は、同じチーム・seedを使うヘッドレス試合とPygame描画試合を別々に実行する。固定ステップ数、得点、選手位置・スタミナ・行動、ボール、イベント、試合時計、乱数状態を比較し、結果をJSONとして標準出力へ出す。描画にはダミーSDLとCPU描画を使い、実際の `Game.draw()` を呼ぶ。比較中は画面を表示しない。

既定では最大18,000ステップで90分の完走を要求する。短い確認には `--max-steps 300 --allow-partial` を使える。`--seed`、`--home`、`--away`、`--render-every` も指定可能。比較ツールでは `Match(..., record_events=True)` を使い、画面用の最新8件に加えて、試合開始から `add_event()` が出した全ログを比較する。通常の試合では全件記録はオフ。

比較結果には両経路のログ件数・SHA-256と `first_event_difference`（0始まりの配列indexと両側のログ、欠けた側はnull）を含む。差がなければnull。全履歴の内容・順序・発生時刻のどれかが違う場合は `same_state: false` になり、`different_fields` に `event_history` が入る。ハッシュだけで一致を判定せず、実データ同士を比較する。

## 入力条件の保存と再実行

`--save-input <JSONパス>` は、比較を始める前に両チームの開始時データと計算条件をUTF-8で保存する。出力先の親フォルダは先に作成する。既存ファイルは上書きしない。開発ログの保存先にはGit管理外の `user_data/logs/` を使う。

```text
python -m scripts.tools.match_repro_check --seed 12345 --venue NEUTRAL --save-input user_data/logs/match-input.json
python -m scripts.tools.match_repro_check --load-input user_data/logs/match-input.json
```

形式は `format: kadocalcio.match-repro-input` / `version: 1`。`teams.home` / `teams.away` はチームID・選手能力・監督・戦術等を含む正規化済み入力の複製で、元チームファイルの編集・移動・削除に依存しない。通常のチーム編集用JSONやリーグセーブとは別形式とし、小数の能力値も丸めない。`settings` は `seed`、`venue_mode`、`ai_rethink_multiplier`（0.5〜3.0）、`fixed_physics_dt`（0.05）、`max_steps` を保持する。

`--load-input` 時は記録したチームと設定を両経路に渡す。`--home` / `--away` / `--seed` / `--max-steps` / `--venue` / `--ai-rethink-multiplier` の同時指定は受け付けない。描画間隔 `--render-every` と未完走を許す `--allow-partial` は選択できる。描画には通常の `Game.draw()` を利用するため、スタジアム等のアセットとPygameは必要。

`commands` は空配列を記録する。version 1は外部操作なしの自律試合が対象で、空でないCommand列や未対応の形式バージョン・固定ステップを読み飛ばさず拒否する。同じエンジン実装・設定定数・Python環境での再実行用であり、将来のAI・物理変更前の挙動を保存するエンジンアーカイブではない。

## 入力エラーの診断

再現入力の `ai_rethink_multiplier` は、boolを除く整数または小数で0.5〜3.0を指定してください。アプリはNaN・無限大・範囲外の値を拒否し、極端に大きい整数でも内部の数値変換例外を漏らしません。有効な倍率の値や型、seed、固定ステップ、チーム能力、保存形式は変更しません。

保存入力の倍率を検査する時は、既存のJSONを `--load-input` で指定してください。倍率が不正な場合、アプリは対象設定名を含む入力エラーを標準エラーへ出し、終了コード2を返します。診断した値を許可範囲へ修正してから再実行してください。終了コード1は不一致・未許可の未完走であり、入力形式のエラーとは区別してください。

## CLI・比較・保存の担当

CLIの引数処理やファイル保存を変更する際に、固定更新や描画比較まで読み直さずに済むよう、担当を分けています。利用者の実行方法は従来どおりです。Gitルートで `python -m scripts.tools.match_repro_check --help` を実行してください。アプリは利用できる引数を表示し、試合を開始しません。

| 担当 | ファイル |
|---|---|
| 既存のコマンド入口と同条件の描画有無比較 | `scripts/tools/match_repro_check.py` |
| 引数定義、入力の選択、実行順、CLI終了診断 | `scripts/tools/match_repro_cli.py` の `MatchReproductionCli` |
| UTF-8 JSONの読込と排他的な新規保存 | `scripts/tools/match_repro_files.py` |
| 再現入力v1の作成・復元・検証 | `scripts/tools/match_repro_input.py` |

CLIは入力の復元を確認してから、要求された入力を比較前に保存します。比較処理が結果を返すと、一致・不一致や完走の判定より前に、要求された全ログ付きレポートを保存します。保存に失敗した場合は終了コード2で停止します。既存ファイルを上書きせず、親フォルダを自動作成しません。保存先を確認してから再実行してください。

開発者は `python -m unittest discover -s tests -p "test_match_repro*.py" -v` を実行してください。試験は保存順、既存ファイルの保持、BOM付き入力、設定の引渡し、ダミーSDLでの実描画比較を確認します。実ウィンドウの操作や90分完走の検証とは区別してください。

## 全ログを含む調査レポート

`--save-report <JSONパス>` は比較完了後、UTF-8の新規ファイルに `format: kadocalcio.match-repro-report` / `version: 1`、再実行入力の `input`、比較結果の `comparison` を保存する。`comparison.event_history.headless` / `rendered` に開始からの全ログが入る。各ログは1始まりの `sequence`、試合内秒数の `game_time`、セットプレー準備中も進む `simulation_elapsed`、`text` を持つ。表示文面が同じイベントも通番を分けて残す。

```text
python -m scripts.tools.match_repro_check --load-input user_data/logs/match-input.json --save-report user_data/logs/match-report.json
```

不一致やステップ上限による未完走もレポートへ保存したうえで終了コード1を返す（`--allow-partial` 指定時は一致した未完走を許容）。標準出力には全ログを省いた要約だけを表示する。出力先は既存フォルダ内を指定し、既存ファイルは上書きしない。レポートの `input` は入力形式version 1そのもので、別JSONへ取り出して `--load-input` に渡せる。レポート全体は `--load-input` の直接入力ではない。

## 表示ログと全イベント記録の契約

表示用の最新8件と、再現性調査用の全件記録を混同しないため、別の列として扱います。通常の試合は既定で全件記録を無効にし、比較ツールは明示的に `record_events=True` を指定します。表示ログは最新順、全件記録は発生順です。全件記録は `Match.add_event()` が発生時の数値と文面を `MatchLogEvent` に写して保持します。

同じ試合内秒数・同じ演算経過秒数に同じ文面を二度出した場合も、別々の通番を持ちます。通番はキックオフを1として増えます。セットプレーの準備中は試合内時計が止まり、演算経過秒数は選手等の移動に合わせて進みます。ログの照合では、文面や試合時計だけで重複を除かないでください。

`event_history()` は、その時点の変更不可の記録値をtupleで返します。取得後に新しい記録を追加しても、取得済みのtupleは増えません。`to_payload()` は独立した辞書を返すため、その辞書を書き換えても内部の記録は変わりません。`start_new()` は内部の履歴を消し、次のキックオフを通番1として記録します。ただし、同じMatchでの再開始は乱数器を初期化しないため、同seedからの再現試験には新しいMatchを使ってください。

開発者はGitルートで `python -m unittest discover -s tests -p test_match_event_history.py -v` を実行してください。試験は表示上限、記録順、値の独立性、記録有無による乱数・状態の一致、再開準備中の両時計を確認します。全試合の物理イベントや90分完走を網羅する試験ではありません。通常の利用者に追加の操作はありません。
