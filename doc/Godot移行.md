# Godot移行の作業地図

正本は [移行管理 #119](https://github.com/tomiya7688/kadocacio/issues/119) と各実装Issue。ここは入口と依存の索引であり、進捗の固定コピーを置かない。

## 優先順位と一回の作業

1. リモートをfetchし、現在のGitルート・変更・PRの依存順を確認する。未マージPRの状態を捨てない。
2. 依存待ちの移行Issueのうち、前提Issueが完了したもの、または前提PRの実装・テスト・CIが成功したものだけ blocked を解除する。PRが未マージならその検証済みブランチへ積む。
3. `start_task.bat` で実装Issueを1件だけ選ぶ。明示番号は自動選択を迂回するので、依存待ちの番号を渡して前提を飛ばさない。
4. 当該Issueの最小範囲を実装し、関連テスト・全体回帰・必要なGodot実行/画像/実機確認を行い、互換性・未検証条件を区別する。
5. 変更履歴・クラス一覧・作業地図を更新し、コミット・push・PRを作る。検証成功した実装Issueは in-review とし、PRをIssueに関連付ける。完了条件を満たすまではIssueを閉じない。
6. 次の依存が満たされたか確認し、着手可能な後続だけ blocked を解除して引き継ぐ。親Issue自体を実装タスクとして選ばない。

`task_selection.json` は編集可能な自動選択方針。P0かつbugラベルの重大バグ → godot-migration の着手可能Issue → 通常の P0/P1/P2/P3/優先度なし。同じグループは優先度、Issue番号順。tracking/blocked/in-review は自動対象外。既存のPygame見た目追加や移植を妨げない全体リファクタは後回しにする。

## 移行時の契約

- 型付きGDScriptを基本とし、UI/表示と、Nodeの無い試合演算・データモデルを分ける。1クラス1ファイル・1責務を移行先でも守る。
- Python/Pygameは比較用に維持。移行先が合格するまで通常入口を変更・旧コードを削除しない。既存巨大クラスをそのままGDScriptの巨大クラスへ写さない。
- 表示、ヘッドレス、リーグ、チューナーは移行先の同じ演算核を使う。移行途中の二重実装は検証用だけとし、本番の異なる判定分岐を残さない。
- 最大0.05秒の固定ステップ、実時間1秒で試合10秒、90分、倍速1/2/3/5/10/100、セットプレー準備中の独立時計を維持。時計だけで高速完走しない。
- 3D表示、選手サイズ/目/モーション、ボール追従と酔い対策、観客1席1人とレア観客、既存の編集/リーグ機能を移す。
- 能力0..5500、旧スケール/日本語・英語キー、忠実さ0..100、自由なFW/MF/DFと7～11人/GK、監督、全スキル、選手タイプ、能力ごとの作用を維持する。
- JSONの初期値とセーブ内の能力を区別し、全年度履歴・旧セーブ・複数テンプレートの互換を試験する。teams/カルチョビット/とユーザーセーブは公開/破壊/一括変換しない。
- PythonとGodotのRNG/浮動小数点は同一seedだけで一致すると仮定しない。比較fixture、乱数の契約、許容誤差、主要結果/イベントの比較基準を先に作る。
- 90試合（表示1＋ヘッドレス89）のカクつき/完走/CPU/メモリは実測する。移行しただけで高速化したと宣言しない。必要なC++拡張はプロファイル後に小さい別Issueへ分ける。

## 現時点の検証境界

起動基盤・チーム読込API・実エンジン検証手順・Pythonとの対応は [`godot/README.md`](../godot/README.md)。#120ではGodot 4.7.2を固定し、型チェック、正常/異常fixture、ウィンドウ/ヘッドレス起動・終了を扱う。#121ではNode無しの読み取り専用モデル/診断を追加し、Python由来の契約と公開チーム/合成ケースで正規化・原本保持を照合する。通常入口はPythonのまま。

試合演算・3D試合表示・旧セーブのGodot読込・移行後の性能は未実装/未検証。各Issueの検証済みPR/CIを確認して次へ進む。
