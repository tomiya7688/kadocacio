# 試合エンジン境界（移行中）

## 現在の入力契約

`Match(home_choice, away_choice, venue_mode="HOME", *, ai_rethink_multiplier=1.0)` は、読込・正規化済みの両チームを必須とする。チームJSONの探索、選択、読込はアプリ・リーグ・評価等の呼び出し側で行う。片方が欠けた場合、試合層は代わりのチームを探さずにエラーを返す。

この境界は `static_analysis/architecture_rules.json` の `match-no-team-loader` で監視する。試合層から `scripts.team.team_data` を再びimportしない。

## 確定結果（Result）

`Match.final_result()` は `FULLTIME` 後のみ、変更できない `MatchResult` を返す。得点・シュート数・支配率・得点者・試合内時間を値として複製し、試合の可変オブジェクトは渡さない。`winner` は `HOME` / `AWAY` / `DRAW`。`to_payload()` は既存リーグ結果キーを保ち、JSONへ変換できる値を返す。表示試合の確定処理と裏試合の完走結果はこの契約を利用する。ステップ上限で未完走なら確定結果を作らず、従来の途中経過を診断用に返す。

## 試合中の状態（Snapshot・部分導入）

`Match.status_snapshot()` はスコアボード用の `MatchStatusSnapshot` を返す。両チームの略称・得点、試合時計、状態、バナー、倍速をその時点の値として複製し、画面はチームの可変オブジェクトを直接読まずに表示できる。試合途中から取得でき、過去のSnapshotはその後の試合更新で変わらない。生成は描画時のみとし、固定ステップ内に追加の割り当てを持ち込まない。

## 未完了の外部契約

試合ログの観測には `Match(..., record_events=True)` と `Match.event_history()` を利用できる。`add_event()` が出した全メッセージを発生順の不変 `MatchLogEvent` として保持し、取得時はtupleへ複製する。各要素は1始まりの通番・試合内秒数・セットプレー準備も含む演算経過秒数・文面を持つ。`start_new()` で履歴と通番をリセットする。既定は記録オフで、通常画面用の `events` は従来の最新8件を維持する。永続化は呼び出し側が `to_payload()` で行う。

これは既存メッセージの観測契約であり、文面を解析してルールを動かさない。ログを発生させない接触等の全物理イベントや、種別・選手IDを持つ構造化されたドメインイベントは対象外。

Commands / 全画面・選手状態のSnapshot / Events はまだ安定した公開APIではない。スコアボード以外の画面・リーグ実装には `Match` の可変内部状態を直接読む箇所があり、この文書だけで移植可能になったとは扱わない。#22 の段階的な境界整理で読み取り状態と操作・イベントを定義し、呼び出し側を順次移す。

`scripts/core/simulation_geometry.py` は現時点でPygame座標型を包む交換点であり、完全なPygame非依存化も未完了。
